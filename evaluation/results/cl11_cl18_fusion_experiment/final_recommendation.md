# Final Recommendation

**Is the CL11/CL18 demotion pattern reproducible?** Yes — exactly, via an offline RRF recomputation validated against the frozen production ranking (exact rank match for both queries, using fixed depth-40 candidate lists and an empirically-determined fusion constant, k=1).

**Is it genuinely caused by fusion?** Yes, confirmed, not merely probable. Both targets are present in both branches (previously mis-reported as absent from sparse due to the prior audit's insufficient top-20 saved depth — corrected here via fresh depth-40 retrieval). The demotion is the direct, reproducible mathematical consequence of RRF combining a strong dense rank with a weak-but-present sparse rank.

**Does reducing sparse contribution improve Constitution retrieval?** Yes, modestly — macro MRR 0.856→0.908, nDCG@10 0.884→0.922 (offline-baseline to 0.5-weight), with only one small individual regression (C13).

**Does that reduction damage case-law retrieval?** Yes, substantially for one query (CL01), which drops from nDCG@10 1.000 to 0.500 — CL01's target is found *only* via a strong sparse signal (dense finds nothing for it at all), so weakening sparse's contribution directly weakens the one mechanism that makes CL01 retrievable.

**Which queries regress under each setting?** At 1.0/0.75: none detected beyond the macro-level case-law decline. At 1.0/0.5: **CL01 (large)** and **C13 (small)**. No other regressions found across the 33-query set.

**Is there enough evidence to justify further fusion testing?** Yes, but **not for an across-the-board weight change** — the evidence instead supports **per-query-characteristic-aware** fusion tuning (e.g., a weight schedule informed by how many branches actually surface a given candidate, or query-dependent weighting), since a single global sparse-weight reduction clearly helps some queries (CL11, CL18, Constitution broadly) while clearly breaking others (CL01) that currently work perfectly. A blanket weight change is not recommended; a smarter, query-aware or score-distribution-aware fusion adjustment is a reasonable next experiment.

**Is a reranker still warranted, or should candidate generation be investigated first?** **Candidate generation does not need further investigation for CL11/CL18 specifically** — both targets already reach both branches' candidate pools; this was the prior audit's open question, now resolved. A reranker remains the more promising lever for CL11/CL18's specific pattern (present-but-fusion-demoted), since reordering an already-correct candidate set is exactly what a reranker is built to do, and this experiment shows the demotion is a fusion-formula artifact, not a missing-data problem. The global sparse-weight reduction tested here is a weaker alternative to a reranker precisely because it cannot distinguish CL11/CL18's case (where weak sparse should be down-weighted) from CL01's case (where weak-but-present sparse ranking 1st is the *entire reason* the target is found) — a reranker operating on a per-document basis could in principle fix the former without touching the latter, whereas a single global weight cannot.

**Single recommended next action:** Do not change the production fusion weight based on this experiment alone. Instead, treat a reranker (or a per-query adaptive fusion weight informed by how concentrated/sparse each branch's own score distribution is) as the next concrete experiment to design, specifically targeting the "present in both branches, fusion-demoted" pattern confirmed here — while explicitly preserving whatever mechanism currently rescues CL01-type queries (dense-absent, sparse-strong).
